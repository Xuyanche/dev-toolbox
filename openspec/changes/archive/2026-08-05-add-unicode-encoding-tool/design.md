## Context

现有 `EncodingTool` 通过 `kind` 在 Base64 与 URL 间复用页面骨架，领域函数集中在 `src/features/encoding/encoding.ts`，工具注册、桌面导航和移动导航统一由 `src/shell/App.tsx` 的定义驱动。Unicode 工具会跨越领域转换、共享页面组件、导航和首页摘要，因此需要在实现前明确转义语义及复用边界。参见 proposal.md 与对应 delta specs。

当前工作区同时存在 JSON 与 JWT 紧凑布局的未提交修改。实现时必须保留这些用户改动，并针对重叠的 `App.tsx`、测试和样式变更做增量编辑。

## Goals / Non-Goals

**Goals:**

- 以确定性的 JavaScript/JSON 兼容格式在普通文本与 `\uXXXX` 间双向转换。
- 让 Unicode 工具复用 Base64 的页面结构和交互行为，同时保持独立组件状态。
- 对畸形转义和不成对代理项提供严格、可操作的错误反馈。
- 保持纯前端、本地处理且不增加依赖。

**Non-Goals:**

- 不提供 `U+1F44B`、HTML 数字实体、URL 百分号、UTF-8 字节或 `\u{1F44B}` 等额外 Unicode 表示法。
- 不实现 Unicode 规范化、字符名称查询、编码探测或文件转换。
- 不改变现有 Base64、URL 或 JSON 字符串转义语义。

## Decisions

### 1. 按 UTF-16 代码单元输出固定宽度转义

编码逐个处理 JavaScript 字符串的 UTF-16 代码单元，每个单元输出小写 `u` 和四位大写十六进制数字。这样 BMP 字符、ASCII 以及补充字符都只有一种规范结果，补充字符自然输出高低代理对，与 JavaScript 和 JSON 字符串字面量兼容。

备选方案是按 Unicode 码点输出 `\u{...}` 或 `U+...`。这些格式对补充字符更直观，但不符合用户确认的 `\uXXXX` 目标，也无法维持固定四位格式。

### 2. 解码采用显式扫描和严格代理项校验

解码器扫描输入，普通文本原样保留；遇到 `\u` 时必须读取恰好四个十六进制数字。解出的高代理项必须紧跟一个有效低代理项转义，低代理项不得单独出现。任一错误返回统一失败结果，不产生部分输出。

不使用 `JSON.parse` 包裹输入，因为混合文本可能包含引号、换行或其他反斜杠序列；借用 JSON 解析器会无意引入与 Unicode 转义无关的 JSON 字符串规则。宽松替换正则也不采用，因为它容易保留畸形转义并产生误导性的部分结果。

### 3. 扩展现有 EncodingTool 的 kind 分派

将 `kind` 扩展为 `base64 | unicode | url`，用每种 kind 的配置决定标题、说明、占位文案及运行函数。URL 专属模式继续只在 URL 页面显示；Unicode 与 Base64 保持同样的设置数量和两栏布局。

相比复制一个 `UnicodeTool` 组件，扩展现有组件能直接继承交换、复制、清空、状态和响应式结构，降低两个页面日后发生视觉漂移的风险。领域编码/解码函数仍保持独立导出，便于单元测试。

### 4. 通过统一工具定义接入所有导航

在编码工具数组中把 Unicode 定义插入 URL 与 Base64 之间，同时扩展 `ToolId`。桌面与移动导航继续从同一数组派生，避免两套顺序不一致；首页摘要显式加入 Unicode。

## Risks / Trade-offs

- [所有 ASCII 也会转义，结果比仅转义非 ASCII 更长] → 页面说明和测试明确“每个代码单元均转换”，换取稳定、可预测且真正双向的编码格式。
- [普通文本中偶然出现字面量 `\u` 会被视为转义开始] → 对格式错误给出明确提示；需要保留该字面量时不应执行解码。
- [共享组件继续增加条件分支后可读性下降] → 将 kind 差异收敛到小型配置和单一转换分派，不把领域解析逻辑放入 JSX。
- [导航与测试文件和当前未提交工作重叠] → 实施前检查差异并采用最小增量补丁，禁止覆盖或回退现有改动。

## Migration Plan

1. 添加纯函数与领域单元测试，不改变现有转换行为。
2. 扩展共享编码页面并增加 Unicode 组件交互测试。
3. 注册导航与首页摘要，更新桌面和移动端顺序、数量及状态测试。
4. 运行完整测试、类型检查和构建；失败时仅回退本变更新增的 Unicode 注册与逻辑，不触碰其他未提交修改。
